# Working Rules for AI Agents and Contributors

These rules are binding for any agent (or human) implementing Hikasa.

## 1. Scope discipline
1. Implement requirements by ID. A pull request names the IDs it implements
   (`Implements FC-050, FC-051`) and does not change unrelated behaviour.
2. Do not invent features that are not in `docs/`. If a requirement is ambiguous,
   write the interpretation into the relevant doc in the same PR (keep docs the single
   source of truth).
3. Priorities are binding: finish P0 of a milestone before starting P1 work.

## 2. Code rules
1. Rust stable, edition 2024, `#![forbid(unsafe_code)]` in every crate except an
   explicitly audited low-level crate.
2. Engines are pure (no I/O, no UI); I/O goes through `hikasa-vfs`; UI through
   `hikasa-app` only.
3. Public APIs are documented (`#![deny(missing_docs)]` in library crates).
4. Errors: `thiserror` enums in libraries, `anyhow` only in binaries. No `unwrap()` on
   user-controlled data; no panics in jobs (panics are caught and reported).
5. Long operations take a `CancellationToken` and report `Progress`.
6. No new dependency without: license check (`cargo deny`), a line in
   `docs/02-tech-stack.md`, and a justification in the PR.
7. All user-visible text goes through the localization table.
8. Formatting and lints must be clean (`cargo fmt`, `cargo clippy -D warnings`).

## 3. Tests
1. Every engine change ships with unit tests and, where applicable, property tests
   (`proptest`) and golden fixtures under `tests/fixtures/`.
2. Every bug fix adds a regression test.
3. Benchmarks for performance-sensitive paths (`criterion`), compared against the
   previous run in CI (no more than 10 % regression without justification).
4. GUI logic is tested through the command catalogue and view-model layer, not by
   screenshot.

## 4. Documentation
1. Update the relevant `docs/*.md` when behaviour changes; add new requirement IDs
   rather than renumbering existing ones.
2. Keep `docs/reference/commands.md` in sync with the command catalogue (generated by
   `cargo xtask commands-doc`; CI fails if the file is stale).
3. Write the user manual topics (`help/`) in parallel with features; the F1 context
   help maps command ids to topics.

## 5. Independence and naming
1. This project is an original work. Do not copy code, assets, icons, help text,
   file-format definitions or settings files from any other comparison product; do not
   reference other products by name in code, docs, commit messages or help.
2. Use the vocabulary in `docs/00-overview.md` §2 consistently (session, view, spec,
   rules, orphan, section, …).
3. File extensions owned by Hikasa: `.hksnap` (snapshot), `.hikasa-pkg` (settings
   package), `.hikasa-session` (exported single session).

## 6. Git workflow
1. Branch per requirement group (`feat/fc-filters`, `fix/tc-crlf-save`).
2. Conventional commit messages (`feat(folder): implement name filters (FC-050)`).
3. PRs must pass CI and include a short "How to verify" section.
4. Version bumps only on release branches; `Cargo.toml` versions stay in lockstep
   across the workspace.

## 7. Communication with the user/maintainer
1. When a decision point in the docs is reached (e.g. the GUI performance gate,
   ARCH-GUI-003), stop and report measurements before switching technology.
2. Report partial completion explicitly: what is done, what is skipped and why.
